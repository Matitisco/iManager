# Dominio propio para Firebase Auth

`VITE_FIREBASE_AUTH_DOMAIN` es opcional y acepta un hostname, sin `https://`, path ni barra final. Vacía o ausente conserva `gen-lang-client-0137016082.firebaseapp.com` para popup, sin cambiar el login actual. iOS standalone conserva su excepción existente: redirect con helpers del mismo origen. No se cambian projectId, apiKey, appId, usuarios ni proveedor Google.

Para que el popup diga «continuar a app.imanager.com.ar», completar **todos** estos pasos antes de habilitar la variable. Este cambio de código no configura Firebase, Google Cloud ni Railway automáticamente.

1. **Firebase Console**, proyecto `gen-lang-client-0137016082`: Authentication → Settings → Authorized domains → agregar `app.imanager.com.ar` (solo hostname). Conservar `gen-lang-client-0137016082.firebaseapp.com` y los dominios de despliegues existentes.
2. **Google Cloud Console**, mismo proyecto: APIs & Services → Credentials → abrir el cliente OAuth 2.0 de tipo Web que usa el proveedor Google de Firebase (su client ID figura en Authentication → Sign-in method → Google → Web SDK configuration). En Authorized redirect URIs agregar exactamente `https://app.imanager.com.ar/__/auth/handler`. Conservar `https://gen-lang-client-0137016082.firebaseapp.com/__/auth/handler`. Si se restringen Authorized JavaScript origins, agregar `https://app.imanager.com.ar`. Si Google requiere verificar el dominio para la pantalla de consentimiento/branding, verificar `imanager.com.ar` y registrarlo allí. No crear un cliente OAuth distinto ni cambiar los IDs del SDK.
3. **Hosting HTTPS/DNS**: `app.imanager.com.ar` debe apuntar al servicio web de Railway y tener TLS válido. Iniciar con `npm start` (`node scripts/serve-spa.mjs`), que sirve `dist` y hace reverse proxy transparente de GET/POST/HEAD de `/__/auth/*` y `/__/firebase/init.json` a `https://gen-lang-client-0137016082.firebaseapp.com`, preservando path, query, status, MIME y body. Nunca responder con el HTML SPA ni un 302 hacia Firebase para sustituir el proxy. Los redirects externos del proveedor sí se preservan.
4. **Railway**, servicio frontend: definir `VITE_FIREBASE_AUTH_DOMAIN=app.imanager.com.ar`, disponible tanto durante **build** (Vite la incorpora al bundle) como en **runtime** (servidor). Redeploy completo; cambiar solo el runtime no actualiza la configuración del SDK. El upstream del proxy sigue fijo al proyecto original para evitar loops y destinos arbitrarios. Con la variable, los redirects internos de helpers Firebase se mantienen en el origen de la app. Sin variable se conserva el proxy previo que necesita iOS standalone. No colocar esta variable solamente en el servicio backend.
5. **CDN/otro servidor**: si no se usa `npm start`, implementar el mismo reverse proxy para ambos prefijos y excluirlos de cualquier caché CDN. No servir un snapshot antiguo de los helpers. Todos los helpers usan `Cache-Control: no-store`; errores de conexión son 502 visibles. No se reenvían cookies de la app ni Authorization al upstream, y POST tiene límite de 64 KiB y timeout de 15 s. El service worker excluye siempre `/__/`, `/api/`, credenciales, dominios externos y queries.

Verificar antes de probar OAuth: `https://app.imanager.com.ar/__/auth/iframe` entrega el helper Firebase, `/__/firebase/init.json` entrega JSON del proyecto y `/sw.js` entrega JavaScript con no-store. Comprobar login Google en desktop/Safari/Android, redirect desde iPhone instalado y retorno a la tienda; cancelar y reintentar. Email/password debe seguir operativo. Las pruebas locales usan identidad ficticia y no reemplazan esta prueba OAuth del dominio desplegado.

## Rollback

Eliminar (o vaciar) `VITE_FIREBASE_AUTH_DOMAIN` del servicio frontend de Railway y volver a construir/desplegar. Popup recupera el dominio Firebase original y iOS standalone mantiene el flujo same-origin anterior. Conservar dominios y URIs autorizados durante la transición: usuarios con un bundle anterior pueden estar terminando OAuth. No borrar usuarios, caches de sesión Firebase ni credenciales OAuth. Verificar popup/email y el helper de iOS tras el rollback. Las actualizaciones PWA se aplican automáticamente cuando no hay un formulario/edición abierto.

Referencia: [Firebase: redirect y reverse proxy de helpers, opciones 1 y 3](https://firebase.google.com/docs/auth/web/redirect-best-practices).
