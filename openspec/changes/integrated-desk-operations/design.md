# Design: integrated desk operations

Use a dedicated `operations` module and service as the only coordinator for cross-module writes. It runs PostgreSQL serializable transactions with bounded retry for serialization/deadlock errors; it uses a tracked local transaction helper rather than relying on local untracked files. All records are store-scoped.

The Prisma schema adds explicit links between an inventory item's manual pending sale registration and its resulting sale, between a trade-in and its received inventory and outgoing sale, plus a separate confirmation state and snapshot of the outgoing item's prior status and pending registration. `StoreNotification` persists one event for every affected section in the same transaction; `NotificationRead` is unique by notification and user. Notification creation is exposed as a small transaction-scoped writer contract for the later notifications route implementation.

Dedicated `/api/operations/:source` routes derive authorization from the originating section. The source grants only the operation and the minimal product/client lookup required by the flow. Mutations return affected serialized records and a brief Spanish summary. Confirm retries return existing linked rows. Cancellation keeps client and history, cancels operation records, archives received stock, restores outgoing stock state, and refuses if received stock has been used.

A draft exchange persists only `TradeIn`. Confirmation creates/reuses its client according to the submitted identity choice, receives the device into `EN_REVISION` at `takeValue` with an absent-price sentinel, and sells the outgoing item for the full outgoing amount. The sale status determines debt: a simple pending sale adds the full amount; a trade adds only the nonnegative difference. Editing a linked operation updates all linked fields and recomputes client aggregates from active sales.

Legacy manual product status updates to `VENDIDO` mark the product as awaiting sale registration and remember the prior status. Imports retain existing behavior. Legacy CRUD is guarded from independently mutating integrated records.

The notifications API lists only persisted events for the active store and sections the member can access. Read state is stored per user; individual and bulk read endpoints are limited to that same visible event set. The Desk loads the persisted feed, merges operation responses immediately, and marks entries read before opening a permitted record. An explicit archived-received event kind opens a read-only detail for the archived device; that read remains scoped to Inventory and never re-adds the device to active stock. A queued record-open action survives hash navigation clearing the modal.

## Backend contract

- `GET /api/operations/:source/options` returns only active, sellable stock (`price > 0`) and client `{id,name}` options. `:source` is `inventory`, `sales`, `tradeins`, or `clients` and authorizes only that operation plus this lookup.
- `GET /api/operations/:source/drafts` lists pending drafts owned by that source; `tradeins` can list all pending exchanges. `GET /api/operations/sales/sales/:id` reads an integrated sale. `GET /api/operations/:source/trades/:id` reads a trade only if the source owns its draft or has access through the linked sale/trade-ins section. These reads do not write notifications or affect other modules' general lists.
- `POST /api/operations/:source` creates a sale or exchange. Payload fields are `date`, `clientId` or `clientName`, `productId` or `deviceLabel`, full outgoing `amount`, `paymentMethod`, `status` (`COMPLETADA` or `PENDIENTE`), `categoryId`, `saleCategoryId`, `customFields`, `requestKey`, `draft`, and optional `tradeIn` (`deviceReceived`, optional `deviceReceivedImei`, `takeValue`, status, battery health, grade, custom fields). A trade-in source defaults to a persisted draft; pass `draft:false` for immediate confirmation.
- `PATCH /api/operations/sales/sales/:id` edits a sale and its linked trade-in/client/stock effects. `PATCH /api/operations/:source/trades/:id` edits a draft, or edits the linked confirmed operation. Sales source may edit a sales-origin draft or linked exchange; trade-ins source may not edit unrelated sales.
- `POST /api/operations/:source/trades/:id/confirm` confirms a pending draft. The trade-ins section can confirm any draft; another source can confirm only its own draft. It accepts merged draft fields and optional `saleCategoryId`; trade-in `categoryId` stays on the trade-in record and is never copied to the sale category.
- `POST /api/operations/:source/trades/:id/cancel` cancels a draft or linked exchange. Sales source may do this only for a linked exchange. `POST /api/operations/sales/sales/:id/cancel` cancels a simple sale or delegates to its linked exchange.
- Successful mutations return `{sale?,tradeIn?,inventory,clients,notifications,summary}`. Archived incoming inventory is included with `archivedAt` so clients can remove it from active stock. Confirmation retries return the same linked records and affected client/stock with no duplicate notifications.
- `GET /api/notifications`, `POST /api/notifications/:id/read`, and `POST /api/notifications/read-all` are protected by notification permission and filter events through the member's section access. Read state is isolated per user within the shared store feed.
- Manual inventory create/update transitions to `VENDIDO` persist an Inventory event; import paths do not emit new events.

Legacy `POST /api/sales` still creates an integrated sale and returns the operation result. Legacy `POST /api/trade-ins` now creates a draft by default; its response retains the `tradeIn` key for compatibility. Legacy edits to integrated records use the shared operation service, and deletion cancels while preserving history. Imported and pre-existing rows retain legacy behavior and null integrated confirmation state.
